# PigPower SmartFarm Platform — Backend (Pass 1, Python/FastAPI)

FastAPI + SQLAlchemy (async) + PostgreSQL backend, rebuilt to match your
existing `backend/app/` folder layout (`api / auth / database / middleware /
models / repositories / schemas / services / utils`), plus two additions —
`storage/` and `events/` — needed for cross-cutting concerns the SRS calls
for (5.3 storage abstraction, 5.4 in-process event system).

This covers the same Pass 1 scope as the architecture docs: Authentication,
Users (self-service), Farmer, Production, Veterinary, Documents (core), and
Sync.

## ✅ This one has actually been run, not just written

Unlike an earlier NestJS/Prisma attempt (which hit a sandbox network
restriction on Prisma's binary downloads), this version was built and
verified against a **real, running PostgreSQL 16 database** in the same
environment that wrote it:

- `alembic revision --autogenerate` correctly detected all 18 tables
- `alembic upgrade head` created them for real
- The seed script ran and inserted districts, roles, permissions, and three
  test users
- A live `uvicorn` server was started and the **full core loop was exercised
  over real HTTP**: login → `/auth/me` → `/sync/reference-data` → create a
  farmer (got back `FMR-000001` from the numbering engine) → scoped farmer
  list → a sync batch with **one valid and one deliberately invalid item**,
  confirming the exact mixed `CONFIRMED`/`REJECTED` response shape from the
  5.5 API spec → a retried sync batch with the same idempotency key,
  confirmed **not** to create a duplicate row in the database

So: this should work for you close to out of the box, modulo your own
`DATABASE_URL` and environment differences.

## What's implemented

```
app/
  main.py            FastAPI app, global exception handlers, middleware, startup events
  config.py          Environment-based settings (pydantic-settings)
  api/v1/             Route handlers (thin — delegate to services)
    auth.py, users.py, farmers.py, production.py, veterinary.py,
    documents.py, sync.py, router.py
  auth/               security.py (JWT/bcrypt), dependencies.py (get_current_user,
                       require_permission — the FastAPI equivalents of guards), types.py
  database/           session.py — async engine/session, declarative Base
  middleware/         request_id.py
  models/             18 SQLAlchemy models across sacm.py, user.py, farmer.py,
                       production.py, veterinary.py, document.py, sync.py
  repositories/       Data-access layer, one per module, thin query wrappers
  schemas/            Pydantic request/response shapes (the DTO equivalent)
  services/           Business logic + orchestration (where events get emitted)
  storage/            StorageDriver protocol + local filesystem driver +
                       signed-URL issuing/verification
  events/             event_bus.py (hand-built pub/sub — Python has no NestJS-style
                       EventEmitter built in) + event_catalog.py + audit_listener.py
  seed.py             Same reference data / test users as intended for the platform
alembic/              Migration environment (async-aware, wired to app.config.settings)
```

## Setup

```bash
cd backend
python -m venv venv          # you already have this from your earlier scaffolding
source venv/bin/activate      # or venv\Scripts\activate on Windows
pip install -r requirements.txt

cp .env.example .env
# Edit .env -- point DATABASE_URL at your PostgreSQL instance.
# Format: postgresql+asyncpg://USER:PASSWORD@HOST:5432/DBNAME

alembic revision --autogenerate -m "init"
alembic upgrade head
python -m app.seed

uvicorn app.main:app --reload --port 8000
```

Interactive API docs (auto-generated by FastAPI) will be at
`http://localhost:8000/docs`.

## Differences from the earlier NestJS attempt (for context)

If you'd previously seen the NestJS version, a few things work slightly
differently here because of language/framework differences, not because of
a different design intent:

- **No global response-wrapping interceptor.** NestJS interceptors can
  transform a return value before serialization cleanly; FastAPI/Starlette's
  response pipeline doesn't offer an equally clean equivalent without
  buffering every response body. Instead, every route handler calls
  `success_envelope(...)` explicitly before returning. Slightly more
  repetitive, functionally identical output.
- **No NestJS-style `@OnEvent` decorators.** `app/events/event_bus.py` is a
  small hand-built pub/sub (`event_bus.on(...)`, `event_bus.emit(...)`) —
  Python doesn't have an equivalent built into any mainstream web framework,
  so this was written from scratch to preserve the 5.1 `AD-SYS-004`
  in-process event design.
- **Guards → Dependencies.** NestJS's `AuthGuard`/`PermissionsGuard` become
  FastAPI dependencies (`Depends(get_current_user)`,
  `Depends(require_permission("farmer.view"))`), declared per-route rather
  than globally — this is just idiomatic FastAPI, not a functional gap.
- **Per-item SAVEPOINTs in the sync service.** Since all items in one sync
  batch share a single outer database transaction, `SyncService` wraps each
  item's dispatch in `db.begin_nested()` so a failed item's partial writes
  roll back without affecting other items that already succeeded earlier in
  the same batch. Worth knowing about if you extend `SyncService` later.

## Known simplifications to revisit

- `AuditListener` (`app/events/audit_listener.py`) only logs structured JSON
  via Python's `logging` module — a later pass should persist these to an
  immutable `audit_log` table per `ACRM FR-ACRM-003`.
- `StorageService` always uses `LocalStorageDriver` regardless of the
  `STORAGE_DRIVER` setting — the branch is there, just not yet implemented
  for MinIO/S3-compatible drivers (5.3 `AD-FS-003`'s future migration).
- `VeterinaryService.schedule()` returns recent records, not an actual
  upcoming-vaccinations-due schedule (depends on SACM §15's configurable
  defaults — deferred to the full Veterinary module pass).
- You'll see a harmless `(trapped) error reading bcrypt version` warning on
  first password hash/verify — this is a known `passlib`/`bcrypt` 4.x
  version-detection quirk, not a real error (verified: login works
  correctly despite it). Pinning `bcrypt==4.0.1` instead of `4.2.0` in
  `requirements.txt` silences it if it bothers you.
- Segregation-of-duties enforcement (`ACRM FR-ACRM-011/012`) isn't
  implemented yet — relevant once Payments/Finance are built in a later pass.
